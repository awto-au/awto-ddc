# Review: .LIB vs vendor firmware, odd `rtk_libsig.py match` results (issue #31)

Generated by `scripts/lib_review.py readme` from `README.head.md` + `verdicts.md` + the .LIB + the vendor banks. Private repo: this document quotes Realtek disassembly (CLAUDE.md exception for `re/lib-review/`).
Disassembly: `scripts/d8051.py` (clean 8051 decoder, `MOV DPTR,#imm` annotated with RTD2795T-CG regdb names; fixups labelled from the .LIB OMF records).

## Summary
- **The vendor library is the same family/build as `RL6449_FunctionLib.LIB`**: 111 of 322 non-short functions in 95 modules are byte-identical modulo link fixups. No patched-library signs: none of the odd results is a byte-level patch of a lib function.
- **Of the 4 "variants", 2 are real source-revision differences and 2 are artefacts.** Real: `ScalerColorRGBOutputGammaAdjust` (different gamma-on bit/register, same table load) and `ScalerColorDCRLocalDimmingReadTHDResult` (vendor body at 0:C119 reads live registers, lib copy reads a stored struct). Artefacts: `ScalerGetDataPortSingleByte` (matched `ScalerGetDataPortWord`'s skeleton), `ScalerColorDCRGetLocalDimmingHistoEnable` (a 11-byte prefix inside another function).
- **Both NEARs are artefacts** (`HLWOutputGammaAdjust`, `HLWIAPSGainAdjust`): 34-byte wrappers differing from the exact-matched `ScalerColorHLWDCRAdjust` (6:6359) in one index constant (0x0E / 0x0F vs 0x0D). Fixed: `rtk_libsig.py` now classes a fuzzy placement that equals another function's EXACT placement as `SIBLING` (4 functions: these 2, `ScalerGetDataPortSingleByte`, `...ReadTHDResult`).
- **`ScalerTcon0..13Enable` ~85%** is a wrapper-shape look-alike (vendor 2:FCE7 sets a bit through the DISPLAY_FORMAT port); the vendor does not call the TCON data port through these wrappers.
- **ABSENT mostly means "module not linked"** (Keil links only referenced modules); only the 2 real variants above show a differing build of a linked module.
- **`ScalerGetDataPortSingleByte` is not hot for us**: nothing in the compiled tree (tmp/sdcc-port/src) calls it (own file + header declaration only); the vendor has no copy. `ScalerGetDataPortWord` matches exactly and has source (`ScalerCommonDataPortAccessGetWord.c`).
- **Unsourced functions**: `srccheck` said 169; two matcher-tool bugs (a `//`-line containing `/*` swallowed code; `using N` suffix functions) inflated it. Correct count 160 for the two trees named in #31, of which 145 have sources under `Kernel/Scaler/ScalerFunction`. **15 have no C source anywhere**: 11 `ScalerMbr*` (Realtek advanced motion blur reduction), `ScalerTconAdjustByIndex`/`ScalerTconEnableByIndex`/`ScalerTconAlternateEnable`, `ScalerAdvance` (1-byte stub). All are absent from the vendor image.
- **Referenced but unsourced**: 13 of the 15 are referenced by compiled `.c` (ScalerMbr.c, ScalerDisplay.c, ScalerMDomain.c, UserCommonInterface.c, RL6449_Series_Scaling.c). The MBR ones sit under `_RTK_ADVANCED_MOTION_BLUR_REDUCTION_SUPPORT == _ON`; `Kernel/Common/RL6449_Project_Default.h` sets that and `_MOTION_BLUR_REDUCTION_SUPPORT` to `_OFF`, so the build needs no stub as long as they stay OFF. The 3 advanced-TCON helpers are called from ScalerMbr.c only. Nothing in the 15 is wanted (vendor does not use advanced MBR).
- **HDMI Ethernet / HEC / HEAC (issue #32)**: nothing. No function in either .LIB has HEC/HEAC/Ethernet/ARC/CEC/SCDC/HDMI in its name; the SDK `Kernel` tree has no `HEC`, `HEAC` or `Ethernet` identifier in any `.c/.h`; regdb has no register named so. The libs hold scaler/colour/OSD/DP-access code, not the HDMI RX block.

```c
BYTE ScalerGetDataPortSingleByte(WORD usAddr, BYTE ucValue)
{
    BYTE pucArray[1];
    memset(pucArray, 0x00, sizeof(pucArray));

    ScalerGetDataPortByte(usAddr, ucValue, 1, pucArray, _NON_AUTOINC);

    return pucArray[0];
}
```

**Verdict: different function, matcher artefact (not a build difference).**
- The matcher placement 6:5991 is the EXACT placement of `ScalerGetDataPortWord` (vendor bytes = lib bytes modulo fixups).
- Shared skeleton: `memset(array)`, `ScalerGetDataPortByte(...)`, then return from the array. 77.6% is that skeleton.
- Real differences vs the SingleByte lib body: array/count 2 instead of 1 (`R7` 02 vs 01), `bAutoInc` taken from the bit parameter (`MOV C,20h.6 / MOV 20h.7,C`) instead of the constant (`SETB`), return built from two bytes (`ADD/ADDC` tail) instead of one.
- The vendor image has no placement for the SingleByte body at all (ABSENT even under fuzzy matching with fixups masked): the module is not linked.
- Hot? No. No `.c` in the compiled tree (tmp/sdcc-port/src, RL6449 + common trees) calls `ScalerGetDataPortSingleByte`; only its own file and one header declaration mention it. `ScalerGetDataPortWord` (which the vendor links) has no caller either; the vendor's use comes from its own user code.
