## 1. Is RL6449 our chip (RTD2795T-CG)?
- Method: SDK `Kernel/Scaler/RL6449_Series_Common/Header/RL6449_Series_Common_RegCommonInclude.h` + `RL6449_Series_McuInterface.h` (MCU xdata regs) vs `re/regdb/RTD2795T-CG.tsv.gz` REG rows (9209).
- Register NAME equal at same address: 8830 (RegCommon) + 339 (McuInterface, all our `0xFDxx` MCU regs) = 9169 / 9209 = 99.6%.
- Remaining 40: same address, different name; all indirect data-port slots (e.g. 0x92 OSD data port, 0x25/0x2B/0x31 ports) = naming-style difference in our regdb, not a chip difference.
- Same test, other families (RegCommon only): RL6432 44.6%, RL6410 51.4%. RL6449 is the only fit.
- SDK has 2388 regs we lack = mostly indexed sub-registers of ports (HDMI page 72 etc.); no sign of a missing block.
- ID handling: SDK reads only `ID_REG_02` (0x000F) via a "get ID code" helper; `ID_REG` 0x00 (0xCF) is never read, so 0xCF2 as a whole is not checked anywhere.
- RL6449 version codes: A=0x20, B=0x21, D=0x22, E=0x23. Our chip reads `ID_REG_02` reset 0x21 = RL6449 VER_B. RL6432 also uses 0x20-0x22 (0x21 alone does not discriminate), RL6463 0x10-0x12.
- Verdict: **confirmed as our chip's SDK family** (register map identical to 99.6% by name incl. the version code); not an explicit "RTD2795T" or 0xCF2 string match, because the SDK never uses marketing names.

## 2. OSD font download and VLC glyph blob
Confirms `osd-font-download.md` blob format, and settles two of its open items.
- Blob in flash = 8-byte code map, 2-byte big-endian length, then VLC stream. Confirmed: the SDK macro for table size reads bytes 8-9 big-endian; stream starts at +10.
- Open item "how the map reaches hardware" = settled: the 8 map bytes are burst-written from flash straight to the scaler registers starting at **0x3A0F** (auto-increment, so 0x3A0F-0x3A16). Not via the OSD data port.
- Order in the SDK loader (RL6449 and RL6432 identical; `Kernel/Scaler/RL6449_Series_Scaler/Lib/Code/RL6449_Series_OSD/SRAM/RL6449_Series_OsdHardwareVLC.c`):
  1. `0x3A0B` rotation bits set (bits 7:6 swap, bit 2 hw-rotate enable, bit 0 rotation) per requested orientation.
  2. Burst 8 map bytes to 0x3A0F.
  3. `0x3A17` low 2 bits = decode-compressed + compression enable.
  4. SRAM destination address = `font_base + glyph_index * 9` words (set via the 0x90/0x91 pair).
  5. Burst the stream (length from header) to the OSD data port 0x92.
  6. Wait 2 ms (hardware flushes decoded data to SRAM; a delay, not a poll).
  7. `0x3A17` compression bit cleared; `0x3A0B` restored to non-rotating state.
- 9 words per 1 bpp glyph = 27 bytes = 12x18, matches. A non-compressed sibling loader exists (pass-through decode bit; used for rotation); it also uses a 2 ms-class SPI-interval tweak via an MCU register before the burst.
- Orientation: the SDK stores glyph data in normal orientation and lets hardware rotate at download. Our blobs need no pre-rotation assumption.
- Glyph/char tables in the sample UI ("RTD2014" OSD under `User/RTD Series/RTD2014Osd/Code/`):
  - Glyph sets are C byte arrays of VLC blobs (`RTD2014OsdFontVLC.c`) = generated by Realtek's font tool, committed as arrays. No build step converts a bitmap. The tool is not in the SDK.
  - Separate char-map arrays (`RTD2014OsdFontTable.c`) give glyph indices per cell: row-major, 0xFE = next row, 0xFF = end, 0xFC = skip cell, 0xFD = repeat previous N times.
  - 1 bpp char word written to text SRAM: byte0 = 0x4C (low nibble 12 = cell width in px), byte1 = glyph index, byte2 = colour byte. 90/270 rotated variant uses byte0 0x4E. This differs from the byte0 layout in `osd-font-download.md` section 6 (bit7 visible); that layout came from the older RTD266x model. Re-verify against our dump before relying on either.

## 3. Boot logo / splash
- Draw function: `OsdDispShowLogo` (sample OSD, `RTD2014OsdDisplay.c`). Called once on entering the initial mode state, then backlight on, then a 3 s timer event hides the logo.
- Sequence (ours, no code): pattern generator black, disable OSD, select palette, map OSD as 70 cols x 10 rows, transparency max, load two glyph blobs, put two char-map arrays, position at centre (50%/50%), draw one filled window 839x179 px behind the text in a logo colour, enable OSD. Fade-out = per-frame-step transparency decrement (18-frame step, 7 steps).
- Geometry: 70 x 10 cells x (12 x 18) = 840 x 180 px = the window size. Confirms the 12x18 cell.
- The logo is TWO glyph sets side by side: set 0 = 19 cols x 10 rows, 80 distinct glyphs at font offset 0; set 1 = 51 cols x 10 rows, 71 distinct glyphs at offset 80 (after set 0). Placed at col 0 and col 19.
- The logo is NOT one blob and not 586 glyphs: cells are de-duplicated (blank cell = glyph 0 repeated), the map array carries layout, the blob carries unique glyphs only.
- Implication for our flash: blobs `0x228C6/22BED/231AB/23B41` are glyph sets; the layout (row/col grid of glyph indices) lives in a SEPARATE char-map array in code space. Without that map, blob D's grid cannot be reconstructed by edge matching. Search our dump for runs of small indices with 0xFE row separators ending in 0xFF.
- Logo colours: palette selected before the draw (a logo palette; 1 bpp so fg/bg indices only).
- Source of the image in a build: none in the SDK. Image-to-blob conversion is a Realtek (or customer) font-tool step; only its output arrays are committed. To replace our logo: create the unique-glyph set + char map ourselves (our `scripts/` encoder) and re-link or patch flash.

## 4. Flash / image layout and bank order
- Linker: Keil BL51 6.11 banked, ~17 bank (`BANKAREA(0x0000,0xFFFF)`), project link script `Project/Header/RL6449_Project_Link.lin` includes `Kernel/Link/RL6449_Link.lin`. XDATA 0xD700-0xF6FF reserved. Auto-link tool `Tool/build/auto_link.exe` assigns modules to banks (opaque .exe, flags: sort, hex2bin).
- Only RL6432 Beacon has an `Output/` tree (6 banks). Measured on it (2026-11-04):
  - `.bin` = 393216 B = 6 x 64 KiB; block k = bank k, at file offset `k * 0x10000`, in ascending bank order. Each block is a full 64 KiB 8051 code-space image.
  - Common code area = 0x0000-0x2585, byte-identical in every block (replicated 6x). Bank-private code and tables start above it (e.g. the main global font table is at bank 2 offset 0x2586).
  - `.H00-.H05` = Intel HEX per bank, each H0k matches block k byte for byte (0x0000-0xFFFF window).
  - This matches our flash addressing (bank N offset X = flash `N*0x10000 + X`, e.g. blob at bank 2 off 0x28C6 = `0x228C6`). Bank write order confirmed.
- The RL6449 build likely adds more banks (our dump is larger). `?B_BANK0..?B_BANK16` switch stubs exist in the RL6432 map (17 banks possible).
- Flash partition modes exist (boot/user, optional digital signature, key table at a fixed address near 0xF000 or 0xC000 of a bank) = relevant if our image is partitioned.
- Settings/NVRAM: pages searched by a find-free-page routine in the OSD NVRAM module (wear-levelled pages with checksum + version code).

## 5. Panel config
- Panel headers: `Panel/*.h`; schema example `Panel/EXAMPLE/PANEL_DPTX_EXAMPLE.h`. Fields: link rate (RBR/HBR/HBR2), lane count (1/2/4), vendor-specific type, link-sequence swap, HPD detect, MSA ignore, bit mode, typ/max/min frame rate, FreeSync max/min frame rate, H/V start/width/end/total (+max/min), sync widths, pixel clock (+max/min, unit MHz), T1-T6 power sequencing, line-change limit.
- **No Samsung LTM270FL01** in the SDK. Nearest eDP entries: 30 AUO 27" UHD (HBR2, 4 lanes, 3840x2160, htotal 4200, vtotal 2200, 61.0 Hz max, pixel clock 554 MHz); Samsung ATNA56YX03 (OLED, HBR, 2 lanes).
- Frame rates are in 0.1 Hz units. Most panels 46.0-86.0 Hz; FreeSync entries up to 144.0 Hz (27" LVDS) and 240.0 Hz (27" VBO). So > 60 Hz is a first-class config (max frame rate and total ranges), not a special mode.
- Pixel clock tiers checked by config macros: > 250 MHz warns for single pipe, 1 path <= 400 MHz, 2 path 630-700 MHz, 4 path <= 1200 MHz.
- HBR2 x 4 lane = 17.28 Gbit/s payload; 4K 120 Hz 24 bpp needs ~24 Gbit/s so it does not fit; QHD/FHD > 60 Hz does.
- For LTM270FL01: take timing from the panel's EDID/datasheet; these headers only show which fields the firmware needs.
